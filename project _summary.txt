2. PROJECT OBJECTIVE
======================================================================

PentAiA v2 is an AI-assisted penetration-testing/security-assessment research and learning agent intended for explicitly authorized lab and defensive environments.

The project is designed to combine:
- natural-language interaction
- LangGraph workflow/state management
- LangChain tool calling
- Google Gemini as the LLM
- Python-owned security-tool wrappers
- a shared Kali Linux execution layer over SSH
- deterministic evidence normalization
- explicit target authorization
- exact human approval before state-changing validation
- structured audit and result handling

The core philosophy is:

The LLM decides WHAT capability it needs from the capabilities PentAiA exposes.
PentAiA code decides HOW that capability is implemented safely.
The human decides WHETHER an approval-requiring action is allowed to execute.

Gemini must never receive unrestricted shell access, arbitrary native tool arguments, arbitrary framework commands, or the ability to manufacture approval state.

5. IMPORTANT CONTROL / SECURITY INVARIANTS
======================================================================

These are architectural requirements and should not be weakened while adding features:

1. Gemini has no unrestricted shell.
2. Gemini has no unrestricted Metasploit/native-framework console.
3. Native command lines are constructed by Python wrappers, not by model text.
4. Model-visible parameters should be typed and semantic.
5. Runtime-owned parameters must not be model-overridable.
6. Code-owned constants/defaults must not be model-overridable.
7. State-changing Phase 3 actions require explicit human approval.
8. Approval is tied to the exact proposal signature.
9. Any material change to target/action/parameters makes previous approval stale.
10. Phase 3 target authorization is checked before execution and rechecked at execution time.
11. Protected/denied targets override allowlisting.
12. Unsupported findings must not cause guessed validation actions.
13. Read-only discovery remains separate from state-changing approval paths.
14. Tool results must be normalized conservatively.
15. Exit code 0 alone must never be interpreted as proof of validation success.
16. Credentials/secrets must not enter LangGraph state, browser output, audit records, or logs.
17. Approval state must never be model-supplied.
18. Future GUI/API layers must not allow the browser to call internal wrappers directly.
19. PentAiA never deletes anything on the target. The proof marker is written by the
    approved action and is deliberately left in place when the console closes: it is
    the evidence, and removing it stays the operator's decision on the target itself.
    Do not "restore" marker cleanup - it was removed on purpose, twice.

9b. PHASE 3 EXPLOITATION — VERIFIED END TO END (2026-09-11)
----------------------------------------------------------------------

Before this, the exploitation leg had never once been verified. It was not a
skill or configuration problem: FIVE independent blockers were stacked on top of
each other, and each one hid the next.

1. No PAYLOAD or TARGET was pinned, so the run inherited whatever the installed
   Metasploit build defaulted to. On this lab build the default is a fetch
   stager whose inline handler blocks forever waiting for a callback, so the
   symptom was a silent infinite hang rather than an error.
2. paramiko's Channel.recv_exit_status() waits on an event with NO timeout. The
   timeout passed to exec_command only sets the socket read timeout, so a remote
   process that never exits hangs PentAiA indefinitely.
3. kali_executor left the remote stdin channel open, so any remote command that
   reads stdin blocked until the process was killed.
4. "run" dropped msfconsole into interactive session mode, which then blocked on
   "Abort session 1? [y/N]" and exited 124 even after a session had opened.
5. phase3_results mapped success to "inconclusive" unconditionally, so a real
   pwn could never be reported as one.

What was implemented:

- The predefined operation pins TARGET, PAYLOAD, LPORT and AutoCheck as
  code-owned values. Model-facing parameters are unchanged.
- The Metasploit command is bounded on the Kali side with
  "timeout --signal=INT --kill-after=<n>" and given SSH-side headroom.
- Remote stdin is closed after exec_command.
- The console runs with "run -z" so it does not block interacting with a session.
- normalize_phase3_result() derives the outcome from RETURNED EVIDENCE
  (uid=0(root), command shell session, meterpreter session) instead of assuming a
  clean exit proves anything. Exit code 0 alone still never counts as success.
- PENTAIA_LPORT is runtime-owned: resolved before approval, covered by the signed
  proposal, revalidated immediately before execution, and emitted as "set LPORT".
- phase3_session.py holds the reverse session open for the human: msfconsole runs
  inside a detached tmux session on the Kali host, the console pane is the
  evidence, and the operator takes over with tmux attach + sessions -i <id>.
- phase3_controlled_validation routes reverse-session actions through that held
  session, and its result carries the session name, callback address/port, attach
  command and handoff note. The agent relays the handoff and never claims to have
  typed into the session.

Verified against the authorized lab (Metasploitable 172.16.0.64, Kali
172.16.0.13): the CLI approval prompt shows the resolved lhost/lport; approving
yields outcome "success"; attaching to the held session and running `id` returns
uid=0(root).

Commits: ce24d75, dd549d8, ffaba6f (pushed to origin/main).

LAB-SPECIFIC FACTS DISCOVERED BY TESTING — do not re-derive these blind:

- The lab Metasploit build (Framework 6.5.2-dev) exposes a SINGLE target
  (index 0, "Linux/Unix Command"). "set TARGET 1" fails at run time with
  "Invalid target index".
- "cmd/unix/interact" is NOT available on that build; it is rejected with
  "The value specified for PAYLOAD is not valid".
- The backdoor shell on 6200/TCP executes through "sh", where bash's /dev/tcp
  pseudo-device does NOT exist:
      sh: line 2: /dev/tcp/172.16.0.13/4444: No such file or directory
  so ANY /dev/tcp-based reverse payload (e.g. cmd/unix/reverse_bash) cannot
  connect back on this target. "cmd/unix/reverse_perl" works.
- The backdoor bind listener on 6200/TCP stays bound after the first trigger, and
  the automatic exploitability check then aborts with "Cannot reliably check
  exploitability". That is why AutoCheck is disabled for this action.
- A held session keeps the listener port bound, so a second run refuses with a
  "conflict" until the tmux session is killed.

13. TESTING / DEVELOPMENT WORKFLOW
======================================================================

Standard project commands:

Install/sync environment:
uv sync

Run CLI:
uv run pentaia

Run all tests:
uv run pytest tests -v

WARNING: do NOT run a bare "uv run pytest" from the repository root.
There is no [tool.pytest.ini_options] and no conftest.py, so testpaths is unset.
A bare run also collects src/pentaia/test_*.py, whose module-level code executes
LIVE side effects at import time: real Gemini API calls (test_gemini.py,
test_gemini_tools.py), an SSH session to Kali (test_kali_executor.py) and
"nmap -sV 172.16.0.13" (test_nmap_wrapper.py). Always scope to tests/.

WARNING: the agent is a long-running interactive REPL. `uv run pentaia` loads the
whole package once at startup and keeps it for every prompt in that process, so a
`git pull` during a session does NOT change the code the agent is executing. Only
new processes see new code. `pentaia session <...>` is a fresh process each time,
so the CLI and a long-lived agent can disagree about what the code does.

This cost hours once, and it looked exactly like a bug: a session created by an
agent process started before f558729 (21:13:11) had no lifecycle metadata, because
that revision's start_live_session did not yet call set_session_metadata. The CLI
(new process, new code) then reported the live console as "action: unknown" while
set_session_metadata and list_held_sessions both tested fine in isolation. The
tmux call in the agent log that looked like the metadata write was really
wait_for_session's first capture-pane of an empty pane. ALWAYS restart the agent
after pulling before treating live behaviour as a regression.

Run linting:
uv run ruff check .

15. IMPORTANT CURRENT DESIGN DECISIONS
======================================================================

1. FastAPI was intentionally excluded from the original early phases.
   It is now planned for Phase 4 when the web/multi-user boundary is required.

2. CLI remains important.
   In Phase 4, GUI becomes the normal operational interface while CLI becomes a disabled-by-default local break-glass interface.

3. A separate pentaia-admin utility is planned.
   It must be local-only, privilege-controlled, fixed-function, and must not contain agent/LLM or arbitrary command execution features.

4. Authentication and authorization are intentionally separated.
   Phase 4 handles authentication + accounting.
   Broader RBAC/authorization administration is deferred beyond the initial Phase 4 scope.

5. AD/LDAPS and RADIUS are both planned authentication backends.

6. Persistent memory across application restart is Phase 5, not current Phase 3/4 session behavior.

7. The Test Framework must remain deterministic.
   Code decides whether a supported validation exists.
   Gemini may explain/recommend it.
   Human approval decides whether state-changing execution proceeds.

8. Exact runtime-owned listener values must eventually be shown BEFORE approval.
   P3-14 owns listener address/port allocation and proposal binding.

9. Interactive sessions, if supported, remain code-managed.
   P3-15 must not turn an established session into an unrestricted Gemini shell.
